# Six-block PlanBench comparison

This package adapts PlanBench's **Blocksworld-4ops** problems to one action per
model call. It compares the action-mean baseline and two-step gate specified in
the [English experiment protocol](PROTOCOL.md). The source dataset is
generated by PlanBench's bundled IPC `./blocksworld 4 6` generator. The
original benchmark's one-response, whole-plan task becomes a sequential
interaction for this experiment. This is a new experimental protocol, not an
official PlanBench score.

The protocol is the self-contained English reference for this implementation.
The shared GRPO runtime is bundled in `game24_experiment/` at this directory's
root so this experiment can be run without files outside `experiment/BlocksWorld`.

## Confirmed task rules

The user selected exactly six blocks, no shortest-plan-length filter, one
`pick-up` / `put-down` / `unstack` / `stack` action per response, and no displayed
list of currently legal actions. Each prompt contains the fixed action rules,
the full current symbolic state, and the instance goal. Satisfying all positive
PDDL goal facts stops the trajectory with terminal reward 1.
An invalid response or reaching 16 valid actions without achieving the goal
stops it with terminal reward 0. All model-generated invalid outputs at a state
form one `INVALID` action for action-mean statistics. It is excluded from the
five-*legal*-action gate and second-action selection, as in the confirmed
Game24 invalid-action convention. Infrastructure exceptions abort the run.

The decision-state key includes the current physical arrangement, **remaining
action budget**, and the goal; two instances with the same layout but different
goals or remaining budget are not pooled. The remaining budget appears in the
current-state prompt because the 16-action limit affects which decisions can
still succeed.
The transition system is checked against the four action definitions in
[PlanBench's domain PDDL](https://github.com/harshakokel/PlanBench/blob/main/plan-bench/instances/blocksworld/generated_domain.pddl).
The generator's goals are partial `on` relations. The raw PDDL is saved;
`prepare` verifies all six objects, complete initial facts, source hashes,
unique initial-goal pairs, and the shortest length of each instance. Problems
whose shortest plan exceeds 16 remain in the data and are reported by split.

## Independently selected first-run values

The user authorized choosing Blocksworld's remaining first-run parameters.
The numbers below are experimental choices, not PlanBench defaults or claims
of optimal tuning. They were chosen to keep the two arms comparable and to
make the first run's upper-bound decision budget similar to the existing
Game24 comparison.

| Item | Value and reason |
| --- | --- |
| Dataset | 500 unique six-block instances: 400 train, 50 validation, 50 test. SHA256 ranking after generation fixes the split without filtering difficulty. |
| Model and update scope | `Qwen/Qwen3-4B-Instruct-2507`, immutable revision locked at `prepare`; LoRA on `q/k/v/o/gate/up/down_proj`, rank 16, alpha 32, dropout 0. Matching the existing Game24 configuration allows code and resource reuse. |
| Method parameters | `ω=1`, `λ=0.5`, `β=1.5`; independently fixed for this first run. They retain the established gate comparison and moderate advantage changes, with no parameter search. |
| Objective | Per-token clipping `ε=0.2`, per-token KL `κ=0.01` against the frozen initial model. The bundled shared method code supplies the exact state-action grouping, first 20% visit selection, five observed legal actions, sigma gate, overlap rule, and trajectory/step/token reduction. |
| Optimization | AdamW, learning rate `1e-5`, weight decay 0, no gradient clipping, one update per on-policy batch. No extra regularizer or stale-data reuse. |
| Training budget | One pass over 400 training problems, 8 per update, 128 sampled trajectories per problem, 3 paired seeds (`20260926`–`20260928`): 50 updates per arm and seed. The maximum is 819,200 action responses per run; actual calls are logged. |
| Generation | Raw-policy sampling, temperature 1, top-p 1, top-k 0, at most 32 generated tokens per action. The emitted EOS token participates in training; padding after EOS does not. A response without EOS is an invalid action. |
| Evaluation | One greedy interactive attempt per problem, with success rate as the primary metric. Validate initially, every 10 updates, and at the end; choose highest validation success, earliest update on ties. Test that selected checkpoint once. |

The two arms use the same generated problems, split, prompt, model revision,
training settings, terminal reward, invalid-action handling, and evaluation
rule. Each arm samples from its own current policy. The baseline applies only
`A^state`; the two-step arm applies the confirmed gate, `λ`, `β`, and overlap
formula. Baseline gate diagnostics remain counterfactual and are not applied
to its updates. Both runs log physical legal-action counts and *observed*
distinct legal-action counts separately. The five-action gate uses the latter.
The summary separately counts states with at least five physically available
actions and states with at least five actions actually observed in old rollouts.

The maximum attempted training decision count is
`400 × 128 × 16 × 2 arms × 3 seeds = 4,915,200`. Actual count can be much
smaller because goals and invalid actions stop trajectories. The 16-step cap
can make some unfiltered instances impossible to solve; their number is
reported rather than hidden.

## Dataset and run sequence

Run these commands from `experiment/BlocksWorld` on Linux. The pinned
PlanBench source revision is
`1f4d600f4806bedbefebbbe44b168372aaf5060d`. Build or restore its
`bwstates.1/bwstates` and `4ops/2pddl/2pddl` executables first:

```bash
python -m blocksworld_experiment.generate \
  --planbench-checkout /path/to/PlanBench \
  --output data/blocksworld6 --count 500
python -m blocksworld_experiment.audit data/blocksworld6 \
  --output data/blocksworld6-audit.json
python -m unittest discover -s tests -v
python -m blocksworld_experiment.train prepare \
  --config blocksworld_experiment/experiment.json \
  --output runs/blocksworld6-plan
```

`generate` calls the original generator sequentially with `4 6`, rejects
duplicate and initially solved problems as the PlanBench wrapper does, and
keeps every other valid problem regardless of plan length. It records the
source revision, binary hashes, candidate calls, exclusions, and every PDDL
hash. The bundled `./blocksworld` wrapper has no seed argument; preserving
the exact generated files and hashes is therefore essential. `prepare`
requires network access to lock the model revision and EOS/padding IDs, and
does not start training.

Install CUDA PyTorch appropriate for the GPU and the packages in
`requirements.txt`. On the external GPU, run each arm for
each seed in the plan, using a separate empty directory:

```bash
python -m blocksworld_experiment.train run --plan runs/blocksworld6-plan/plan.json \
  --output runs/bw6-baseline-20260926 --arm baseline --seed 20260926
python -m blocksworld_experiment.train run --plan runs/blocksworld6-plan/plan.json \
  --output runs/bw6-two-step-20260926 --arm two_step --seed 20260926
```

Repeat for seeds `20260927` and `20260928`. After all six complete:

```bash
python -m blocksworld_experiment.summarize --output runs/bw6-summary.json \
  runs/bw6-baseline-20260926 runs/bw6-two-step-20260926 \
  runs/bw6-baseline-20260927 runs/bw6-two-step-20260927 \
  runs/bw6-baseline-20260928 runs/bw6-two-step-20260928
```

The run manifest saves final effective model, LoRA, optimizer, generation,
and data settings. Per-update files save all trajectories, prompts, token
log-probabilities, action means, gate decisions, and applied advantages.
Initial and post-update audit checkpoints allow source and parameter review;
the paired summary refuses incomplete runs or a changed plan. It reports
success by seed, the paired difference, a problem-bootstrap interval
conditional on the recorded seeds, gate passage, and model-call budgets.

## Verification status

The local symbolic environment, official-style PDDL parsing, exact shortest
plan search, invalid-action handling, and method integration can be checked
on CPU. Actual 500-instance generation requires the upstream Linux binaries;
the pretrained 4B training and outcome comparison require the external GPU.
No Blocksworld training result has been produced by this repository yet.
