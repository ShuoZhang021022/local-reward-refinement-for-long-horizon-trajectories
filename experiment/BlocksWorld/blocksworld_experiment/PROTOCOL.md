# Six-block Blocksworld experiment protocol

This document describes the implemented comparison in English. It is a
task-specific adaptation of PlanBench Blocksworld-4ops to sequential model
interaction, **not** an official PlanBench score. The executable settings are
in [`experiment.json`](experiment.json); the implementation is in this package
and reuses the bundled `game24_experiment` action-mean and token-objective
code. This document is the complete English method and task protocol for
the uploaded experiment.

## Authority and status

The user confirmed exactly six blocks, no shortest-plan-length filter, one
action per model response, no displayed legal-action list, terminal reward 1
only on goal achievement, immediate termination with reward 0 for an invalid
response, at most 16 **valid** actions, and success rate as the primary
metric. The previously confirmed action-mean baseline and two-step gate are
reused. The model, numerical coefficients, dataset size and split, training
budget, optimizer, and evaluation schedule below are independently selected
first-run choices authorized by the user. They are neither PlanBench defaults
nor established optimal values.

The official generator and pretrained-model training have not run in this
workspace. Local CPU checks use synthetic PDDL fixtures and scripted or
mocked model behavior. No six-block success rate, actual shortest-plan
distribution, or observed gate passage rate is available yet.

## Problems and interactive environment

The dataset generator calls the pinned PlanBench IPC script as
`./blocksworld 4 6`. It retains 500 distinct, initially unsolved six-block
PDDL problems and excludes no problem by shortest-plan length. The raw PDDL,
generator revision and file hashes, candidate-call count, rejected duplicate
and trivial counts, and each instance hash are saved. The upstream script has
no seed parameter; the saved files define the dataset. A SHA256 ranking of
those fixed files produces 400 training, 50 validation, and 50 test problems.

The symbolic environment implements the four PDDL operators: `pick-up`,
`put-down`, `unstack`, and `stack`. A goal succeeds as soon as **all** positive
PDDL goal facts hold; it need not specify a complete final arrangement.
Every prompt contains fixed operator rules, all current symbolic facts, the
goal facts, and the remaining valid-action budget. It contains neither the
current legal-action list nor previous conversation turns. The model must
emit one action such as `unstack a b`; the parser normalizes it to the stable
action key `unstack(a,b)`.

A syntactically invalid response, an action with unsatisfied preconditions,
or a response that reaches the generation limit without an EOS token ends the
trajectory immediately with reward 0. Achieving the goal ends it with reward
1. After the 16th valid action, an unmet goal ends with reward 0. The
decision-state key contains the physical facts, the goal, and the number of
actions remaining. Thus equal arrangements with different goals or budgets
are not pooled for advantage estimation.

The exact shortest plan is found by breadth-first search over unit-cost
actions and recorded for every problem. Problems requiring more than 16
actions stay in every relevant split and are counted; they cannot succeed
under this protocol. A constructed six-block example requires 20 actions in
the local symbolic domain, so a six-block limit alone does not make 16
actions sufficient. This example is not claimed to be in the generated data.

## On-policy batch and shared action-mean advantage

One training update uses eight training problems and 128 sampled trajectories
per problem, for 1,024 trajectories. The entire batch is generated by the
current policy before its single parameter update. The two arms begin from
the same pinned model and use the same problems, prompts, budgets, reward,
invalid-action convention, reference policy, and objective. Each arm later
samples from its own evolving policy. Statistics are recomputed within each
update; there is no cross-update replay buffer.

For a complete decision state \(s\), let \(\mathcal I(s)\) be the observed
decision *visits* in the batch, and \(\mathcal U(s)\) their distinct observed
actions. Repeated visits to the same state, including visits by one
trajectory, are counted separately. If \(R_i\in\{0,1\}\) is trajectory
\(i\)'s terminal reward, define

\[
q_s(a)=\frac{1}{|\mathcal I(s,a)|}
       \sum_{(i,j)\in\mathcal I(s,a)} R_i,\qquad
\bar q_s=\frac{1}{|\mathcal U(s)|}\sum_{a\in\mathcal U(s)}q_s(a),
\]

\[
\sigma_s=\sqrt{\frac{1}{|\mathcal U(s)|}
       \sum_{a\in\mathcal U(s)}(q_s(a)-\bar q_s)^2},\qquad
A^{\mathrm{state}}(s,a)=
\begin{cases}(q_s(a)-\bar q_s)/\sigma_s,&\sigma_s>0,\\
0,&\sigma_s=0.
\end{cases}
\]

The distinct action means are equally weighted in \(\bar q_s\) and
\(\sigma_s\); the subsequent policy objective still contains every sampled
visit, without inverse action-frequency weighting. All invalid model
responses at one state form the single observed action `INVALID`. It
participates in action-mean statistics but is not a legal action for the
five-action gate or second-action selection.

The **baseline** uses \(A^{\mathrm{state}}\) at every visit. It computes
two-step diagnostics for comparison, but none of their corrections is applied
to its gradients.

## Two-step gate and final visit advantage

At a parent state with \(K=|\mathcal I(s)|\) visits and \(\sigma_s>0\), the
two-step arm selects exactly \(\lceil K/5\rceil\) visit positions with the
smallest \(|A^{\mathrm{state}}|\). It samples uniformly without replacement
when the cutoff is tied. The selected positions are preserved, while their
first actions are deduplicated before testing the child-state gate.

For each candidate action, the child state uses **all** old visits reaching
that state. A candidate passes only if the child has at least five distinct
*observed legal* next actions, positive child action-mean dispersion, and
\(\sigma_{\mathrm{child}}\geq\omega\sigma_{\mathrm{parent}}\). The first-run
\(\omega\) is 1. Physical legal-action count is recorded separately and does
not substitute for the observed count. `INVALID` can contribute to the
child's action-mean dispersion but cannot satisfy the legal-action threshold
or enter the selected second-action set.

For a passing child, \(A_2\) is its signed action-mean advantage from the
same old visits, so \(A_2=A^{\mathrm{state}}\) at that child. Among its
\(d\) observed legal next actions, select \(\lceil d/2\rceil\) with the
largest \(|A_2|\), breaking boundary ties randomly. There is no additional
sample-count reliability gate or positive/negative quota.

Let \(B\) mean that this *visit position* was selected in the first round
and its action's child gate passed. Let \(P\) mean that the immediately
preceding action in the same trajectory has a passing gate, and let \(S\)
mean that the current action is in that gate's selected second-action set.
A prior action can have a passing action-level gate even when its particular
visit position did not receive \(\lambda\). With \(A=A^{\mathrm{state}}\),
the implemented per-visit advantage is:

| Conditions | Applied advantage |
| --- | --- |
| \(B=0\), and no selected second action | \(A\) |
| \(B=1, P=0\) | \(A+\lambda\) |
| \(B=0, P=1, S=1\) | \(\beta A\) |
| \(B=1, P=1, S=0\) | \(A+\lambda\) |
| \(B=1, P=1, S=1\) | \((1+\beta)A+\lambda\) |

The last row is the confirmed overlap rule, not a second independent
training step. The first-run values are \(\lambda=0.5\) and \(\beta=1.5\).
The sign of a selected negative second-action advantage is retained.

## Token objective, update scope, and budget

All model-generated tokens of one action, including EOS, share that action's
fixed visit advantage \(\widehat A_{i,j}\). Prompt and observation tokens
are conditioning context, not policy targets. For each generated token,
the new-to-old probability ratio is clipped with \(\epsilon=0.2\), and the
GRPO-style KL estimator relative to the frozen initial base model is
multiplied by \(\kappa=0.01\):

\[
r_{i,j,k}=\exp(\log\pi_\theta-\log\pi_{\mathrm{old}}),\qquad
D_{i,j,k}=\exp(\log\pi_{\mathrm{ref}}-\log\pi_\theta)
            -(\log\pi_{\mathrm{ref}}-\log\pi_\theta)-1.
\]

The maximized objective averages the clipped policy term minus
\(\kappa D_{i,j,k}\) first across generated tokens within a decision, then
across decisions within a trajectory, then across trajectories. Advantages,
selection decisions, and old/reference log-probabilities are fixed during
that update. Gradients flow through current-policy token probabilities and
update only LoRA parameters. The optimizer is AdamW at learning rate
\(10^{-5}\), with weight decay 0 and no gradient clipping.

The selected model is `Qwen/Qwen3-4B-Instruct-2507`, pinned to an immutable
revision during `prepare`. LoRA targets `q_proj`, `k_proj`, `v_proj`,
`o_proj`, `gate_proj`, `up_proj`, and `down_proj`, with rank 16, alpha 32,
and dropout 0. Training runs one pass over 400 problems: 50 updates per arm
and seed. Seeds are `20260926`, `20260927`, and `20260928`, for six runs in
total. Generation uses raw-policy sampling (temperature 1, top-p 1, top-k 0),
at most 32 generated tokens per action, batches of 16 for generation and
scoring, and a gradient microbatch size of 8. The maximum attempted
training-action generation count is 4,915,200 across all six runs; early
terminal transitions lower the actual count.

## Validation, test, and records

Validation uses one greedy interactive attempt per problem at update 0 and
after updates 10, 20, 30, 40, and 50. The checkpoint with the highest
validation success rate is selected, with the earliest update winning ties.
That checkpoint is tested once on the same 50 held-out problems for each
arm/seed run. The primary result is test success rate. The final summary
reports paired per-seed differences and a problem-bootstrap interval while
holding the three recorded training seeds fixed. That interval does not
quantify uncertainty across new training seeds.

Summed per-update state counts are **not** globally deduplicated across
updates. The current implementation does not explicitly log per-call wall
time, peak GPU memory, or energy use. Training checkpoints are audit
snapshots; automatic resume or retry is not implemented. See
